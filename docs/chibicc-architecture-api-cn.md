# Casting 项目架构与 API 分析

## 1. 项目概览

`Casting` 是一个面向学习用途的 C 编译器项目，使用 C++20 重写了经典教学编译器 `chibicc` 的一部分能力。当前工程的目标不是实现完整 C 标准，而是打通一条清晰、可验证的编译主链路：

```text
源码字符串
  -> 词法分析 Tokenize
  -> 语法分析 Parser
  -> AST + 局部符号 + 类型标注
  -> x86-64 汇编生成 CodeGen
  -> 交由 gcc 链接并执行
```

从入口实现看，程序当前采用“单参数输入源代码字符串、标准输出汇编”的工作模式，入口非常薄，只负责串联各阶段：

```text
ASTContext ctx
  -> Tokenize(argv[1], ctx)
  -> Parser(token, ctx).parse()
  -> CodeGen().generate(prog)
```

这条调用链定义在 `Main.cpp` 中，说明当前架构是典型的单进程、单遍前端加直接后端发射模式，没有单独的 IR 层，也没有独立优化阶段。

## 2. 当前进展判断

### 2.1 已实现能力

结合源码、测试集和提交历史，当前主干已经具备以下能力：

- 整数字面量、标识符、关键字、标点的词法分析
- 表达式优先级解析：赋值、相等、比较、加减、乘除、一元运算
- 控制流：`if/else`、`while`、`for`、`return`
- 语句块与空语句：`{}`、`;`
- 局部变量声明：`int a;`、`int a=3;`、`int x=3, y=5;`
- 指针类型与操作：`int *p`、`&x`、`*p`
- 指针算术：`ptr + int`、`ptr - int`、`ptr - ptr`
- 多函数定义与函数调用
- 最多 6 个整数参数的 x86-64 System V ABI 调用约定
- 统一的 `ASTContext` 对象所有权管理

### 2.2 当前项目所处阶段

如果按“教学编译器演进路线”来判断，这个仓库已经跨过了“算术表达式解释器”阶段，进入了“可编译一个小型 C 子集并生成真实机器汇编”的阶段。它不是最早期原型了，已经具备以下特征：

- 前端链路完整：词法、语法、基础语义、代码生成全部连通
- 支持多函数程序，而不只是单个 `main`
- 局部变量、参数、指针、循环、函数调用已形成较完整的最小语言子集
- 有集成测试而不是仅靠手工验证

但它还没有进入“接近实用编译器”的阶段，因为以下关键能力仍缺失：

- 只支持 `int` 和指针，没有 `char`、数组、结构体、联合体
- 没有全局变量、字符串字面量、`sizeof`、预处理器
- 没有从文件读取源码，也没有目标文件/可执行文件输出流程
- 没有中间表示、优化、寄存器分配
- 没有完整的函数类型检查、参数数量检查和更丰富的错误位置信息

从提交历史看，这个项目的演进路径比较清晰，基本符合小型编译器逐步扩展的节奏：

## 4. 总体架构

## 4.1 构建架构

`CMakeLists.txt` 采用“静态核心库 + 可执行程序”的结构：

- `casting_core` 静态库包含 `diagnostic.cpp`、`tokenize.cpp`、`parser.cpp`、`codegen.cpp`、`type.cpp`
- `Casting` 可执行文件只包含 `Main.cpp`
- `ctest` 通过 `test.sh` 触发集成测试

这种划分虽然简单，但已经体现出明确分层：

- 前后端逻辑集中在 `casting_core`
- 入口层只做编排，不承载编译细节
- 测试从最终可执行行为验证全链路

## 4.2 运行时流水线

```text
argv[1] 源码字符串
  -> Tokenize
     输出 Token 单链表
  -> Parser::parse
     输出 Function 单链表
     每个 Function 持有 body AST、locals、params
  -> add_type
     在解析过程中对语句做递归类型补全
  -> CodeGen::generate
     输出 x86-64 AT&T 汇编到 stdout
  -> 外部 gcc
     负责汇编、链接和运行
```

这里有两个关键架构特点：

1. 这是“直接生成汇编”的编译器，没有 IR 层。
2. 类型分析不是单独的全局 pass，而是在 `compound_stmt()` 中每解析完一个语句就调用一次 `add_type()` 递归补全。

## 4.3 内存与对象所有权架构

这是项目当前比较成熟的一部分。

`ASTContext` 统一持有以下对象的 `std::unique_ptr`：

- `Token`
- `Node`
- `Obj`
- `Function`
- `Type`

Parser 和 CodeGen 只保留裸指针进行遍历与引用，不负责释放。这种设计的优点是：

- 避免手工 `delete`
- 明确对象生命周期和释放时机
- 各阶段接口仍保持轻量，遍历代码简单

但它也有一个明显特征：虽然底层已经统一管理内存，AST 和符号结构本身仍是“裸指针关系图”，不是基于 `unique_ptr` 的树状所有权表达。因此当前设计是“集中式对象池 + 裸指针引用”，而不是“节点层级直接拥有子节点”。

## 5. 编译主链路详解

## 5.1 入口层

入口逻辑非常直接：

1. 校验命令行参数个数必须为 1
2. 创建 `ASTContext`
3. 调用 `Tokenize()`
4. 构造 `Parser`
5. 调用 `parse()` 得到函数链表
6. 调用 `CodeGen::generate()` 输出汇编

这意味着当前程序的“产品接口”非常小：

- 输入：一段 C 源代码字符串
- 输出：汇编文本
- 错误处理：打印错误后直接 `exit(1)`

## 5.2 词法分析阶段

词法分析器负责把源字符串转成单链 Token 流。

### 已识别的 token 类型

- `PUNCT`
- `IDENT`
- `NUM`
- `KEYWORD`
- `EOF_TK`

### 已支持的关键字

- `if`
- `else`
- `return`
- `for`
- `while`
- `int`

### 已支持的多字符运算符

- `==`
- `!=`
- `>=`
- `<=`

### 词法阶段特征

- Token 内容使用 `std::string_view` 指向原始输入切片
- 关键字识别不是在扫描时直接分类，而是在生成链表后通过 `convert_keyword()` 二次转换
- EOF token 会显式挂到链尾
- 所有 token 通过 `ASTContext::make_token()` 创建

这个 lexer 的定位很明确：为当前支持的 C 子集服务，不追求完整 C 语言词法覆盖。

## 5.3 语法分析阶段

Parser 采用典型的递归下降实现，表达式层级如下：

```text
expr
  -> assign
  -> equality
  -> relational
  -> add
  -> mul
  -> unary
  -> primary
```

### 语法阶段的几个关键设计

#### 1. 函数是当前唯一的顶层单元

`parse()` 会循环解析直到 EOF，并把结果串成 `Function` 链表，因此项目当前支持多个函数定义。

#### 2. 局部变量使用链表维护

`locals` 是 Parser 当前函数上下文中的局部变量链表头。每次 `new_lvar()` 都头插，所以变量链顺序与源码顺序相反。

#### 3. 函数参数单独保序

由于 `locals` 是倒序链表，而参数在生成代码时需要按照 ABI 原始顺序对应寄存器，所以 `Function` 额外维护 `params_` 数组保存参数对象的源码顺序。

#### 4. 声明会在语法阶段被“降级”为赋值语句块

例如：

```c
int x = 3, y = 5;
```

不会保留一个“声明节点”到后端，而是被转换成：

- 新建局部变量 `x`、`y`
- 对带初始化器的部分生成 `ND_ASSIGN`
- 把这些赋值封装进一个 `ND_BLOCK`

这说明当前 AST 更偏向“可直接生成代码”的 lowered AST，而不是保留原始语法细节的高层 AST。

#### 5. `while` 和 `for` 共用一个节点类型

`while` 被编码成 `ND_FOR`，只是复用 `condition` 和 `then` 字段，不单独引入 `ND_WHILE`。这降低了后端复杂度，但也让 AST 语义表达更偏实现导向。

#### 6. 函数参数与返回值当前都围绕 `int`

虽然已经有 `TY_FUNC` 类型，但目前调用和返回路径实际仍以整数/指针为主，没有更完整的函数签名检查。

## 5.4 类型分析阶段

类型模块当前不是一个复杂的静态类型系统，而是一个足以支撑当前代码生成的最小系统。

### 目前类型种类

- `TY_INT`
- `TY_PTR`
- `TY_FUNC`

### 类型传播规则

`add_type()` 会递归遍历节点并给表达式补上 `Node::ty`：

- 数字字面量和比较结果为 `int`
- 变量节点类型来自 `Obj`
- 赋值、算术、一元负号默认沿用左值/操作数类型
- `&expr` 生成 `ptr(expr_type)`
- `*expr` 要求操作数是指针类型
- 函数调用默认返回 `int`

### 当前类型系统的特点

- 足够支撑指针算术和解引用
- 没有独立的类型检查错误恢复
- 没有参数类型匹配校验
- `TY_FUNC` 主要用于声明信息承载，尚未形成完整的函数类型语义闭环

## 5.5 代码生成阶段

CodeGen 直接把 AST 映射为 x86-64 Linux AT&T 汇编。

### 生成器特点

- 输出目标是 `stdout`
- 假设 System V ABI
- 局部变量全部分配在栈上
- 使用简单的表达式栈 `push/pop` 策略
- 通过标签序号生成控制流标签

### 局部变量布局

在生成函数前，会遍历 `locals` 链表为每个变量分配偏移：

- 每个局部变量固定占 `8` 字节
- 栈空间最终按 `16` 字节对齐

这与当前语言子集是匹配的，但也暴露了一个事实：后端目前默认“以 8 字节槽位处理局部值”，这对只有 `int` 与指针的阶段足够简单，但当未来引入 `char`、数组、结构体时，这套布局策略就必须升级。

### 函数调用生成

- 参数表达式先逐个求值并压栈
- 再倒序弹到 `rdi/rsi/rdx/rcx/r8/r9`
- 最后发出 `call`

这与当前“最多 6 个参数”的能力边界一致。

## 6. 核心数据结构

## 6.1 Token

`Token` 是词法分析的基本单元，核心字段包括：

- token 类型 `TokenKind`
- 单链表后继 `next`
- 数字值 `val`
- 原始文本切片 `content`

当前设计非常轻量，适合单遍 parser 直接消费。

## 6.2 Type

`Type` 是最小类型描述结构，包含：

- `kind_`
- `base_`：指针基类型
- `return_ty_`：函数返回类型
- `param_types_`：函数参数类型数组

这说明项目已经有了把“声明语法”映射到“类型结构”的基本能力，而不是纯粹无类型 AST。

## 6.3 Obj

`Obj` 表示一个局部变量，记录：

- 变量名
- 类型
- 栈偏移
- 链表后继

它既承担前端符号表角色，也承担后端栈槽描述角色，是前后端共享的数据结构。

## 6.4 Function

`Function` 表示一个函数定义，包含：

- `body_`：函数体 AST
- `locals_`：局部变量链表
- `params_`：保序参数数组
- `stack_size_`：栈帧大小
- `next_`：函数链表
- `name_`：函数名

这个结构是“程序级单元”的核心节点。

## 6.5 Node

`Node` 是项目最核心的数据结构之一。它既服务表达式，也服务语句和控制流。

### 当前节点种类

- 算术：`ND_ADD`、`ND_SUB`、`ND_MUL`、`ND_DIV`、`ND_NEG`
- 比较：`ND_EQ`、`ND_NE`、`ND_LT`、`ND_LE`
- 基础值：`ND_NUM`、`ND_VAR`
- 语句：`ND_EXPR_STMT`、`ND_RETURN`、`ND_BLOCK`
- 控制流：`ND_IF`、`ND_FOR`
- 指针：`ND_ADDR`、`ND_DEREF`
- 调用：`ND_FUNCALL`
- 赋值：`ND_ASSIGN`

### Node 的结构特点

同一个 `Node` 类通过多个可选字段复用为不同语义：

- `lhs/rhs` 用于表达式树
- `next` 用于语句链
- `body` 用于块语句
- `condition/then/els/init/inc` 用于控制流
- `var` 用于变量引用
- `args` 用于函数调用参数链

这是一种典型的小型编译器 AST 设计：字段复用强，编码效率高，但类型安全与语义清晰度不如细分节点类。

## 7. API 介绍

这里的 API 主要指项目的命令行接口和核心源码接口。由于该仓库不是对外发布的 SDK，因此这些 API 本质上是“项目内部模块接口”。

## 7.1 命令行 API

### 可执行程序

```bash
./build/Casting 'int main() { return 42; }'
```

### 输入契约

- 必须传入且只传入一个命令行参数
- 参数内容是一整段 C 源码字符串
- 当前不支持源码文件路径作为输入

### 输出契约

- 正常情况下向标准输出打印 x86-64 AT&T 汇编
- 出错时向标准错误打印错误信息并退出

### 典型使用方式

```bash
./build/Casting 'int main() { return 42; }' > tmp.s
gcc -static -o tmp tmp.s
./tmp
echo $?
```

## 7.2 `ASTContext` API

`ASTContext` 是对象工厂和生命周期容器。

### 主要接口

| 接口 | 作用 |
| --- | --- |
| `make_token(...)` | 创建并托管 `Token` |
| `make_node(...)` | 创建并托管 `Node` |
| `make_obj(name, ty, next)` | 创建并托管 `Obj` |
| `make_function(...)` | 创建并托管 `Function` |
| `get_int_type()` | 获取全局复用的 `int` 类型 |
| `make_ptr_type(base)` | 创建指针类型 |
| `make_func_type(return_ty, params)` | 创建函数类型 |

### 使用约定

- 返回值都是裸指针
- 生命周期由 `ASTContext` 统一托管
- 调用者只持有引用，不负责释放

这是当前项目最关键的基础设施 API。

## 7.3 Tokenizer API

### `Token* Tokenize(char* Input, ASTContext& ctx, const char* filename = "<input>")`

作用：

- 扫描源码字符串
- 生成 Token 单链表
- 把节点交给 `ASTContext` 管理
- 返回链表头

注意点：

- `filename` 参数当前未实际参与诊断输出
- Token 文本使用 `std::string_view` 引用输入串，因此输入字符串必须在解析期间保持有效

### `bool Tkequal(Token* TK, const char* op)`

作用：

- 判断当前 token 文本是否等于某个符号字符串

### `void Tkskip(Token*& TK, const char* op)`

作用：

- 断言当前 token 为指定内容
- 若匹配则前进到下一个 token
- 若不匹配则报错退出

这是 Parser 最基础的消费接口。

## 7.4 Parser API

### `explicit Parser(Token* tk, ASTContext& ctx)`

作用：

- 用 token 流和上下文初始化 parser

### `Function* parse()`

作用：

- 从当前 token 位置开始解析直到 EOF
- 返回程序中所有函数定义组成的链表头

### 对外可见的辅助接口

| 接口 | 作用 |
| --- | --- |
| `consume(op)` | 如果当前 token 是 `op` 就消费并返回 `true` |
| `expect(op)` | 要求当前 token 是 `op`，否则报错 |
| `check(op)` | 只检查当前 token，不前进 |
| `peek()` | 查看当前 token 指针 |
| `peek_content()` | 读取当前 token 文本 |
| `is_followed_by(str)` | 判断下一个 token 是否为指定文本 |
| `advance()` | 消费当前 token |

### Parser 的内部关键 API

| 接口 | 作用 |
| --- | --- |
| `declspec()` | 解析基础类型说明符，当前只支持 `int` |
| `declarator()` | 解析指针声明器和函数参数列表 |
| `declaration()` | 解析局部变量声明 |
| `stmt()` | 解析语句 |
| `expr()` / `assign()` / `equality()` / `relational()` / `add()` / `mul()` / `unary()` / `primary()` | 递归下降表达式体系 |
| `funcall()` | 解析函数调用 |
| `function()` | 解析单个函数定义 |
| `new_add()` / `new_sub()` | 处理带类型意识的指针算术 |

### API 设计评价

Parser 的 API 设计是“单类集权式”的：

- 好处是逻辑集中、调用路径直观
- 代价是 `parser.cpp` 体量最大、承担职责最重

这也是当前项目最核心、最复杂的模块。

## 7.5 Type API

### `bool is_integer(Type* ty, ASTContext& ctx)`

作用：

- 判断类型是否为 `int`

### `Type* get_ty_int(ASTContext& ctx)`

作用：

- 获取上下文中的整数类型

### `void add_type(Node* node, ASTContext& ctx)`

作用：

- 自底向上递归推导并写入 AST 节点类型

这个 API 虽然小，但它直接决定了：

- 指针算术是否合法
- 解引用是否合法
- 后端生成时各节点的语义是否完整

## 7.6 CodeGen API

### `void generate(Function* prog)`

作用：

- 遍历函数链表
- 分配局部变量偏移
- 生成每个函数的汇编

### 内部关键接口

| 接口 | 作用 |
| --- | --- |
| `assign_lvar_offsets()` | 计算每个局部变量栈偏移与函数栈帧大小 |
| `store_function_params()` | 把 ABI 参数寄存器写回本地栈槽 |
| `gen_addr()` | 生成左值地址 |
| `gen_expr()` | 生成表达式 |
| `gen_stmt()` | 生成语句 |
| `align_to()` | 做 16 字节对齐 |

### 当前后端约束

- 面向 x86-64 Linux
- 采用 AT&T 汇编语法
- 只覆盖当前 AST 子集
- 没有寄存器分配器，依赖栈临时保存

## 7.7 Diagnostic API

### `error_at(loc, msg)`

- 按文本片段位置打印错误并退出

### `error_tok(tok, msg)`

- 以 token 为中心报错并退出

### `fatal(msg)`

- 打印通用致命错误并退出

### 现状评价

诊断系统已经把“错误输出”从业务逻辑中抽离出来，但目前还只到“打印 token 片段”的层级，没有行号、列号和源码上下文。

## 8. 关键设计解读

## 8.1 为什么 `ASTContext` 是当前架构的核心

如果没有 `ASTContext`，这个项目会面对典型的小型编译器问题：

- Token、AST、符号、类型对象大量散落分配
- 生命周期难以梳理
- 很容易出现泄漏和悬垂指针

当前用一个上下文统一托管，等价于引入了一个轻量级 arena/owner 层。这是这个仓库从“能跑”走向“结构可维护”的关键一步。

## 8.2 为什么 Parser 是最大模块

从代码规模上看，`parser.cpp` 远大于其它核心模块。这不是偶然，而是当前架构决定的：

- 语法规则都集中在一个类中
- 声明解析和表达式解析都在这里
- 局部变量管理也在这里
- 一部分语义降级逻辑也在这里

因此项目的“复杂度中心”不是后端，而是 Parser。

## 8.3 AST 是“代码生成友好型”而不是“语法保真型”

当前 AST 的特点是：

- 字段复用强
- 声明被提早 lowering
- `while` 复用 `ND_FOR`
- 参数列表与语句列表都借助链表连接

这说明它更像“面向代码生成的工作 AST”，而不是面向 IDE、重写器、静态分析器的高保真 AST。

## 8.4 类型系统是“够用即可”的最小闭环

当前类型系统的职责不是做完整语义分析，而是服务三件事：

1. 支持变量类型记录
2. 支持指针算术
3. 支持解引用合法性判断

从这个角度看，它已经完成阶段性目标，但还没有发展成完整的类型检查器。

## 9. 当前能力边界与限制

### 9.1 语法与语义边界

- 只支持 `int` 及其指针
- 不支持数组、结构体、联合体、全局变量
- 不支持 `char`、字符串字面量、`sizeof`
- 不支持预处理器和头文件展开
- 不支持从文件读取源码

### 9.2 后端边界

- 只支持 x86-64 Linux
- 只支持整数/指针值路径
- 只实现最多 6 个参数的寄存器调用约定
- 没有优化阶段

### 9.3 工程化边界

- 诊断信息较弱
- 测试以黑盒集成为主，缺少更细粒度单元测试
- API 以内部调用为主，没有稳定库接口承诺

## 10. 后续最合理的演进方向

如果继续沿当前架构推进，优先级比较合理的方向通常是：

1. 补类型系统
   - 增加 `char`、数组、`sizeof`
2. 补对象模型
   - 全局变量、字符串字面量
3. 补更完整声明能力
   - 数组声明器、更完整函数签名检查
4. 补后端稳健性
   - 参数上限检查、类型大小驱动的栈布局
5. 补输入与诊断
   - 从文件读取源码、输出行列号错误信息

如果目标仍是教学价值最大化，那么“数组 + sizeof + 全局变量”会是下一批收益最高的能力。

## 11. 结论

这个项目当前已经具备一个小型 C 编译器的完整骨架，而且不是停留在概念层面：

- 构建链路完整
- 编译主链路完整
- 核心子集可执行
- 测试可验证

其架构最重要的三个特征是：

1. `ASTContext` 统一所有权，解决对象生命周期问题
2. `Parser` 作为复杂度中心，承担语法、局部符号和部分 lowering 逻辑
3. `CodeGen` 直接从 AST 发射汇编，整体路径短、教学可读性高

从“项目进展”判断，它已经完成了一个教学型编译器的中前期阶段，下一步最值得推进的是：扩展类型系统、补足数据对象能力，以及提升诊断和后端稳健性。
